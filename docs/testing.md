# 测试与证据

测试结论按包、版本和架构记录。声明 `x86_64` / `aarch64` 表示配方有对应来源；不能据此标记“已构建”或“Omarchy 可用”。macOS 上的语法检查和归档检查不代替 Linux 构建、ELF 依赖解析或运行测试。

首次落地的实际结果和未验证项目见 [验证记录](validation.md)。

## 验证层次

| 层次 | 验证内容 | 能证明什么 |
| --- | --- | --- |
| 配方检查 | Bash 语法、目录、元数据、URL、校验和 | 配方可供继续审阅 |
| 来源检查 | 下载、哈希、归档布局、二进制架构、许可证 | 当前固定的上游文件匹配 |
| Linux 构建 | 各架构构建、包内容、依赖检查 | 安装包确实生成 |
| 安装生命周期 | 干净系统安装、升级、卸载 | 包管理流程正常 |
| 运行验证 | 实际架构及 Omarchy 会话中的功能 | 已测试环境下功能正常 |

每次发布至少记录前四层结果。GUI、后台服务或账户流程不能仅凭 `--version` 判定通过；未具备测试环境的项写“未验证”并说明环境缺口。

## 静态与来源检查

在仓库根目录执行 `tools/check-package`，或指定一个 `pkgbase`；需要联网核对官方发布信息时执行 `tools/check-updates <pkgbase>`。工具需要 Python 3.9+。没有 `makepkg` 时，静态检查输出不应被理解为 `.SRCINFO` 已通过官方生成结果校验。

审阅 `PKGBUILD` 后，在包目录执行 `bash -n PKGBUILD`。检查文件来源使用 HTTPS、固定版本、下载名没有跨架构复用、普通二进制来源没有跳过哈希。列出归档，确认二进制指令集、文件权限、许可证和有无被遗漏的运行资源。

在 Linux 中执行 `makepkg --verifysource`。对本地包装器检查 Bash 语法；有 ShellCheck 时检查包装器，但注意 PKGBUILD 的专用变量和数组不能机械地按普通脚本警告处理。

## 隔离构建与双架构

在 Arch Linux 上安装 `base-devel`、`devtools`、`namcap`；x86_64 推荐在干净 chroot 中构建：

```bash
cd pkgbuilds/<pkgbase>
extra-x86_64-build
namcap PKGBUILD
namcap ./*.pkg.tar.zst
```

chroot 中的构建能发现被开发机上额外软件掩盖的依赖。[Arch 干净 chroot 流程](https://wiki.archlinux.org/title/DeveloperWiki:Building_in_a_clean_chroot)、[namcap 手册](https://man.archlinux.org/man/namcap.1.en)

`aarch64` 使用实际的 Linux ARM 构建机或明确配置的仿真环境，并记录发行版/镜像和架构。不要在普通 x86_64 Arch 容器里只设置 `CARCH=aarch64` 或使用 `--ignorearch` 就宣称 ARM 构建通过。容器中未运行 systemd、缺少桌面和设备的限制应保留在记录里。

若在 Omarchy 官方包仓库的 fork 内验证，可使用其容器构建工具；命令见 [发布流程](publishing.md)。`--dry-run` 只显示计划，不构建也不验证配方。

构建后用 `pacman -Qip <安装包>`、`pacman -Qlp <安装包>` 检查元信息、依赖和文件列表。检查 ELF 所需共享库时，在目标 Linux 的隔离环境中运行检查工具；不要在宿主机执行不熟悉来源的二进制。

## 安装、升级、卸载

在可恢复的 Arch/Omarchy 测试机或虚拟机中：

1. `sudo pacman -U <安装包>`，确认依赖可满足、无文件冲突和意外安装钩子。
2. 用普通用户检查命令路径、权限、版本和帮助；核对实际启动文件属于当前安装包。
3. 升级到新版本或更高 `pkgrel`，确认配置保留、旧文件清理正确、自更新没有覆盖包管理器文件。
4. `sudo pacman -R <包名>`，确认系统文件和启动入口移除；用户配置、会话及工作数据保留。

每个架构分别完成。运行单元测试或列出压缩包不能替代 `pacman` 安装测试。

## 按软件类型增加检查

- **CLI**：与现有 `qoder` / `qodercli` 等命令共存；空配置首次启动；终端输出；登录流程；用户取消和网络失败；辅助二进制版本约束。
- **后台程序**：安装后没有自动登录或启动；用普通用户手动启动和停止；状态与日志可见；无 root 要求；自启动只在用户显式启用后发生；退出后不遗留进程。
- **GUI**：Hyprland/Wayland 首次启动、图标与搜索入口、文件打开、中文输入、缩放、浏览器登录及 URL 回调；如需 XWayland，记录实际行为和依赖。
- **钉钉等通信工具**：在通用 GUI 检查之外，按需要验证托盘、通知、音视频、摄像头和屏幕共享；设备和门户依赖按实机结果填写。

执行登录或外部功能测试时使用测试账户，不把凭据、令牌、个人消息或完整用户日志提交到仓库。

## 测试记录模板

包目录的 README 或专用测试记录可使用：

```text
日期与提交：
包名及版本（pkgver-pkgrel）：
架构：x86_64 / aarch64
环境：发行版、内核、构建镜像、原生或仿真、桌面会话
来源：下载 URL、SHA-256、清单获取日期
静态检查：通过 / 失败 / 未验证
构建与日志：通过 / 失败 / 未验证；日志位置
安装 / 升级 / 卸载：分别填写
运行项目与结果：
已知限制及未验证项目：
```

CI 产生的构建包和日志是验证证据；它们不是已发布软件源，也不代表有人完成实机登录测试。

## 仓库提供的 CI

[build.yml](../.github/workflows/build.yml)使用固定提交的 Omarchy 官方构建工具，以 `ubuntu-24.04` 和 `ubuntu-24.04-arm` 原生运行对应架构。它构建包，在新的临时容器中检查元数据、安装、主程序动态依赖及卸载；Wake/CLI 额外检查隔离用户目录下的版本和帮助。GUI 不会被当作已完成图形会话测试。

工作流不上传厂商二进制，只保留 GitHub 日志与摘要。首次推送前没有远端构建结论；验证脚本的离线回归测试不能代替真正运行这份工作流。更新官方构建工具固定提交时，重新核对镜像标签、产物路径及构建用户。
